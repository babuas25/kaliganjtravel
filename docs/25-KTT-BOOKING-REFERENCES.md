# KTT booking references

Existing and future bookings use **`KTT` + `YYMMDD` + daily serial**, for example **`KTT260930111111`** for the first booking on 30 September 2026. The year is two digits (`26`). The date comes from the saved booking's `created_at` in `Asia/Dhaka` (Bangladesh time). Time of day is omitted.

Serials start at **111111** for each new Bangladesh date: `KTT260930111111`, `KTT260930111112`, and `KTT260930111113`. The next date starts at `KTT261001111111`. These references are **15 characters**, with no leading zero padding. Serial 999999 supports 888,889 allocations per day; beyond that, the serial grows to seven digits without truncation or collisions. Atomic daily counters serialize concurrent requests. Allocations and historical aliases can leave gaps in the series. A later PNR refresh does not change the reference.

Forward migration **0164** (fresh-install version **20260930000000**) replaces the PNR-based allocator introduced by 0161. Existing STR aliases provide their original daily serial plus 111110 where available. The existing counters advance to cover the new serials. The backfill changes only `public_ref`, preserving every other booking field, including `updated_at`. `booking_reference_aliases` retains both old KTT references and existing STR mappings to the same booking ID. Old booking page links resolve through the same role and visibility checks, then redirect to the new reference. Audit snapshots, notification payloads, and wallet history retain their saved contents. The rename does not enqueue notifications or call a supplier.

Booking routes, ticket management, refunds, SMS, and exact-reference search accept both KTT and legacy STR syntax. Current actions use the canonical reference returned by the booking page. Refresh an already-open old checkout or booking page after rollout.
